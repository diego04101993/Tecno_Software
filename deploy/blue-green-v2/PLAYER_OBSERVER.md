# Observación pasiva de Players

El colector lee sólo el enlace HTTP/1.1 IPv4 entre Edge y la API candidata. El adjudicador asocia la captura con los logs de acceso de Edge y con los heartbeats confirmados por PostgreSQL. Ninguno hace peticiones Player, consulta hashes de tokens ni recibe credenciales Player. Los emuladores que generan tráfico en QA se ejecutan por separado.

## Límites de acceso

El proceso `player_capture.py` necesita Linux x86_64 y acceso al namespace de red de Edge. Ejecútalo en un proceso dedicado, con sistema de archivos en solo lectura, `no-new-privileges`, sólo `CAP_NET_RAW` y sin montar el socket de Docker, claves, credenciales, directorios de aplicación ni volúmenes de datos. `SO_ATTACH_FILTER` selecciona la interfaz y los dos extremos de la ruta aprobada, incluido TCP 8000. `SO_LOCK_FILTER` fija ese filtro. El proceso elimina todas las capacidades después del `bind` y restringe operaciones de red y escritura del socket mediante seccomp. No inicia conexiones ni produce pcap. El proceso sigue teniendo acceso en memoria a los paquetes del enlace permitido, incluidos encabezados y payloads. Sólo emite un identificador de solicitud generado por Edge, clase de endpoint, estado, tiempo y los dos campos mínimos de ACK por su pipe privado. No persistir ni copiar a logs el stdout del colector.

El adjudicador corre como parte del tooling autorizado, en el host del Engine local, con el socket Docker de control y la clave protegida. Sólo inspecciona identidades ya conocidas, lee los logs sanitizados de Edge y ejecuta `SELECT` dentro de `BEGIN READ ONLY` con rollback en PostgreSQL. No imprime filas ni respuestas. Conserva el recibo HMAC con referencias seudónimas y un archivo hermano privado `<receipt>.docker-logs.json` con los registros técnicos sanitizados, separados por stream durante la promoción. Phase 3 conserva su formato de archivo anterior. Ese archivo registra el ID exacto, el intervalo y el hash del comando. La vista de adjudicación usa `docker container logs --timestamps` y ordena por timestamp con precisión de nanosegundos. La clave del firmante nunca entra al colector.

## Secuencia del controlador

1. Ejecutar `player_observer_launcher.py … probe` contra el colector dedicado. Conservar esa comprobación para ambos lanzamientos con `--preflight-receipt`. Mantener los descriptores del colector bajo control de un supervisor de confianza.
2. Iniciar `player_capture.py <interfaz> <ip_edge> <ip_api> 165 --phase3-monotonic --player-latency` antes del switch y esperar `ready`. Usar los IP verificados del Edge y de la API candidata. Mantener stdout en un pipe privado en memoria. El colector requiere haber visto el SYN. Si la captura no termina con `done` o declara pérdidas, la observación falla.
3. Ejecutar la acción `promotion-baseline` del launcher con los argumentos para `player_observer.py … promotion-baseline --socket … --autosave … --bindings … --edge-name …`. El observador comprueba el estado y el READY, toma el baseline fresco y firma `<baseline>.clock.json` en el namespace del colector. `routectl switch-api SLOT <baseline>` valida ambos recibos antes de cambiar la API. El supervisor guarda enseguida `promotion_switch_marker(state, monotonic_ns())` en la línea temporal privada del intento, usando el estado devuelto por el switch.
4. Ejecutar `promotion-observe --timeline …` del launcher con el pipe como stdin y los argumentos para `player_observer.py … promotion-observe --edge-id … --baseline … --socket … --autosave … --bindings … --edge-name …`. Entregar la primera línea preleída mediante `--capture-ready-json` si el supervisor ya la retiró del pipe. El launcher une sólo el namespace temporal e inyecta el hash del estado confirmado y las marcas de la ventana. El observador congela la generación, el slot, el upstream y la identidad READY desde el ledger, el status y la configuración efectiva de Edge. Un cambio del estado durante la observación detiene la adjudicación.
5. Entregar el recibo `PLAYER` firmado a `routectl switch-frontend SLOT <receipt>`. La promoción exige el modo monotónico y la identidad de routing confirmada. El recibo incluye el hash del contexto, las marcas monotónicas, el vínculo con `<receipt>.requests.json` y los conteos de Players observados y faltantes. El CLI devuelve 0 en PASS, 2 ante rechazo adjudicado y 1 ante evidencia incompleta. Un fallo requiere rollback de API y mantiene el frontend en el predecesor.

Una solicitud de la generación previa queda sin crédito. Un ACK tardío de BLUE se anota como `WRONG_SLOT_FOR_OBSERVATION`. Una generación futura o un upstream ajeno a la generación vigente hace fallar el gate. El inicio monotónico de la solicitud decide la pertenencia. El ACK UTC verifica identidad y éxito y puede llegar durante el drenaje. HTTP 401 queda sin crédito. HTTP 409 y 5xx relevantes hacen fallar el gate. Playback requiere HTTP 201 para acreditarse. En ausencia de eventos queda `UNVERIFIED`.

El supervisor debe atar la ejecución a los IDs de Edge, PostgreSQL y slot de la intervención. Los parámetros de red y el pipe forman parte de esa autoridad. El adjudicador no debe aceptar un archivo o una cadena de evidencia aportados por un cliente. La prueba desechable usa un pipe privado desde `docker exec`, las imágenes ya selladas y el Engine local. Su resultado no afirma compatibilidad física de Players productivos.

## Contratos de latencia real en promoción

Edge captura una clase fija antes de cualquier rewrite. Usa el método y el path sin query para identificar `PLAYER_HEARTBEAT`, `PLAYER_RUNTIME_CONFIG` y `PLAYER_PLAYBACK_EVENT`. El resto es `OTHER`, incluido el runtime administrativo. El log de acceso conserva el ID de correlación de Edge, la clase, el ingreso, la generación, el slot, el upstream, el estado y los tiempos. Su filtro elimina la solicitud y los encabezados de la respuesta. Los cuerpos y las credenciales no forman parte de esta evidencia. El colector agrega al pipe del modo de promoción la traza y los instantes monotónicos del runtime nativo, sin emitir su cuerpo. Los logs de Docker conservan stdout y stderr separados y una vista combinada.

`PLAYER_CONTRACT_LATENCY_METRIC=EDGE_TOTAL_DURATION_MS`. Es la duración completa que registra Caddy en `duration` desde el inicio del manejo HTTP hasta el cierre del manejo de la respuesta en Edge. Excluye el tiempo previo a Edge y el procesamiento del cliente. Se conserva la precisión al convertir su representación decimal de segundos a nanosegundos enteros. Los límites estrictos son heartbeat <5 s, runtime <8 s y playback <5 s. `upstream_duration_ms` y `upstream_headers_ms` se guardan para diagnóstico. Este último mide el tiempo hasta los encabezados del upstream.

El observador usa la misma ventana monotónica y el drenaje sellado. Acredita latencia por unión única entre captura y log, con la generación, el slot y el upstream congelados. `<receipt>.requests.json` conserva conteo, máximo en nanosegundos y estado por endpoint. `UNVERIFIED_NO_TRAFFIC` indica que el endpoint no tuvo tráfico en la ventana con evidencia íntegra. El resultado agregado conserva ese estado si falta algún tipo y los observados pasan. Ausencia o ambigüedad de evidencia exigida produce `FAIL_EVIDENCE`. Una violación de latencia de tráfico que sí se observó bloquea el recibo habilitante para frontend. La continuidad conserva el gate y los criterios existentes.

`NEW_BACKEND_TARGET_CONTRACT=5/8/5`. `DEPLOYED_WINDOWS_TIMEOUT_CONTRACT=UNVERIFIED`. Los resultados de la ventana sólo acreditan el tráfico observado.

## Continuidad durante la adopción inicial

Phase 3 usa el mismo colector y adjudicador con `phase3-baseline` y `phase3-observe`. La autoridad es la generación inicial `0` confirmada, API y frontend `BLUE`, y el endpoint IPv4 exacto del backend legacy. La toma de baseline ocurre con el estado preparado y el frontend histórico todavía sirviendo. Su vigencia máxima es 120 segundos hasta abrir el ingreso nuevo. El colector se inicia antes de abrir y la ventana observada comienza con el ingreso verificado, después de la transferencia. El recibo `PHASE3_PLAYER` acredita continuidad de BLUE y queda separado del recibo que autoriza una promoción de frontend.

El adjudicador verifica antes y después el mismo estado, epoch del backend, identidad saludable de PostgreSQL, configuración efectiva y autosave de Edge. Se aplica la misma ventana mínima de 120 segundos y la misma unión de ACK. Un baseline vacío produce `PASS_NO_ACTIVE_BASELINE` y evidencia física sin verificar. Un dispositivo faltante, un 409/5xx o evidencia incompleta requiere la reversión de infraestructura descrita en el runbook Phase 3.

V2.6.4 usa el primer byte observado de cada solicitud upstream para decidir su pertenencia a `[start_monotonic, finish_monotonic)`. Los límites y la duración mínima de 120 segundos se calculan con `CLOCK_MONOTONIC`. El supervisor, el baseline firmado y el colector deben presentar el mismo namespace de tiempo para comparar las muestras. UTC queda en la evidencia de auditoría, en el timestamp del ACK y en la unión exacta con PostgreSQL.

Desde V2.6.5, `player_observer_launcher.py` ejecuta el probe y las dos acciones de Phase 3. Obtiene el PID del colector por ID completo de Docker, imagen, `StartedAt`, `RestartCount`, estado running y ausencia de OOM. Ejecuta `nsenter --target PID --time` y verifica que el proceso lanzado reporta el mismo namespace y el mismo offset monotónico. El observador conserva los demás namespaces del host y accede al socket Docker y a los archivos privados desde el host. Un offset coincidente sólo es válido junto con la identidad exacta del namespace. Tras el arranque, el launcher vuelve a inspeccionar el colector y comprueba el PID, `StartedAt` y namespace antes de autorizar al observador a iniciar el baseline o la ventana.

La evidencia privada del launcher registra los namespaces y ambos valores de `/proc/<pid>/timens_offsets`, los PIDs, `StartedAt`, la versión de `nsenter` y `TIME_NAMESPACE_MATCH`. La comprobación real de `setns` se ejecuta en pre-stage y el recibo se vuelve a validar para cada lanzamiento. Una discrepancia detiene el observador con `PLAYER_MONOTONIC_CLOCK_INVALID`. Si ocurre antes del handoff, R3 conserva el ingreso. Si ocurre después de abrir el ingreso, se aplica la reversión del runbook. El launcher conserva la línea temporal de downtime en el reloj del host. Transfiere la apertura monotónica al dominio del colector usando la diferencia comprobada de offsets. El inicio y el fin de la ventana Player se calculan en ese dominio.

El colector se ejecuta durante los 165 s ya aprobados, desde antes de abrir ingreso. Al cierre de la ventana, el conjunto de solicitudes elegibles queda fijado. Una respuesta de ese conjunto puede completarse durante el tiempo restante de captura. La captura ya marcada `incomplete` o una respuesta posterior al vencimiento del colector producen fallo. El proxy de Players carece de un timeout total por petición configurado. El vencimiento global de captura es el límite de obtención de evidencia terminal y sigue medido desde el inicio del colector.

El lector del pipe conserva el límite de supervisión de 180 s. Usa el arranque monotónico del colector cuando dispone de su prueba de reloj. Hasta recibirla, usa la apertura como límite de respaldo. El supervisor entrega el pipe directamente al observador y pasa el primer registro `READY` ya leído mediante `--capture-ready-json`. Un pipe sin EOF al vencimiento produce un diagnóstico de transporte. El supervisor espera al colector sólo si el observador terminó con éxito. El límite de evidencia terminal de cada solicitud sigue siendo el de la captura de 165 s.

El observador correlaciona cada solicitud admitida por ID exacto, generación, upstream, endpoint y estado HTTP. Los timestamps de Edge se conservan como evidencia. Un evento público de la generación actual sin inicio monotónico correlacionable deja la evidencia incompleta, incluido un 5xx generado por Edge sin conexión al upstream. El archivo privado `<receipt>.requests.json` conserva los instantes de wire y ACK y la decisión por solicitud. El seudónimo sólo se escribe después de una unión única. Los eventos anteriores y posteriores al intervalo quedan sin crédito, aunque su ACK sea válido.

## Evidencia al fallar

El CLI emite `PLAYER_OBSERVER_RESULT`, `PLAYER_OBSERVER_REASON`, `PLAYER_OBSERVER_STAGE`, `PLAYER_OBSERVER_EXIT_CODE` y `PLAYER_OBSERVER_EVIDENCE_PATH` en stderr. Primero intenta crear `<receipt>.failure.json` con modo `0600`, sin reemplazar archivos. Si falla, intenta un directorio temporal privado con un nombre nuevo. Si tampoco puede escribir allí, emite el JSON saneado en una línea de stderr que el supervisor puede preservar. Una terminación del proceso sin oportunidad de ejecutar código requiere evidencia del supervisor.

El diagnóstico registra el tipo de excepción y los marcos del tooling por archivo, función y línea, las etapas actual y anterior, y los conteos que ya se pudieron verificar. Registra UTC para correlación y tiempo monotónico para la duración del proceso. Los límites UTC del gate y el orden de los logs siguen formando parte de la prueba. La captura cruda, los argumentos, la clave, los IDs de Players y sus referencias HMAC quedan fuera del diagnóstico.

| Ruta de salida | Evidencia adicional antes de terminar |
| --- | --- |
| Argumentos inválidos, código 2 | Diagnóstico de argumentos sin repetir valores recibidos. |
| Estado, clave, identidad inicial, salud, transición o ingreso inválidos, código 1 | Causa y etapa. Se conserva el baseline existente. |
| Query del baseline, decodificación, HMAC, revalidación o escritura, código 1 | Causa y etapa. Si se generó un baseline en memoria, conserva su conteo. |
| Lectura del pipe, límite o fallo externo, código 1 | Diagnóstico y conteo de registros si terminó la lectura. El pipe permanece en memoria. |
| Ventana o colección de logs, timeout o escritura de evidencia, código 1 | Diagnóstico y metadatos de cada stream disponible. Los bytes de ambos streams se conservan en el archivo de logs ya previsto si se pudo escribir. |
| Firma del baseline, correlación de logs y captura, o unión de ACK con PostgreSQL, código 1 | Causa, etapa y conteo del baseline si quedó autenticado. |
| Revalidación, validación del fin o publicación del recibo, código 1 | Conteos adjudicados si están disponibles. La durabilidad del recibo se marca como no confirmada si falla la escritura. |
| Gate rechazado, código 2 | Recibo firmado de rechazo y diagnóstico privado con conteos. |

El recibo diagnóstico complementa el código de salida. El supervisor debe exigir una salida exitosa y el recibo HMAC válido antes de acreditar el gate.
